## 1. Forensic finding

A forensic inspection of `formal/` was performed before any file was
modified. The inspection log is attached as
`results/forensic_inspection_2026-11-27.txt`.

### 1.1 What was expected

`results/.preregistration.sha256` (written at freeze, 2026-11-27) records:

    f13fc1b22b82279874d975d2b162284b27040715da363add6e97c303f6d098a4  formal/model_check.sh

This is the SHA-256 of the frozen stub — a short script that only declares
the frozen state space and fails loudly if TLC is invoked.

### 1.2 What was found

`formal/model_check.sh` on disk has SHA-256:

    7cdb8608ee839234c0331501a9c01512843d2f988849b5fc844a2d3967ee0379

It is 31 lines (876 bytes), not the stub. It is a full TLC runner. The
frozen stub is **not present** on disk, in git (the file was untracked),
in any `.bak`, in any editor swap file, in any archive, or anywhere on
the device (searched by SHA).

## 2. Cause

During the pre-pilot implementation phase, the frozen stub was
overwritten with a full TLC runner. The overwriting was not recorded as
an addendum at the time, and no backup of the stub was retained. The
file was also not tracked by git, so `git checkout` could not recover
it. This is a process failure, recorded here in full.

## 3. Resolution

### 3.1 Archive

The state found during forensic inspection is preserved, unmodified, in:

    formal/legacy/2026-11-27_pre_addendum/

with its own `SHA256SUMS.txt`. This archive is documentation, not a
frozen artefact. It may be cited but not relied upon for verification.

### 3.2 Reconstruction of the frozen stub

`formal/model_check.sh` is rewritten to match the documented content of
the frozen stub (see `docs/METHODOLOGICAL_REVIEW.md` §C1 and
`PREREGISTRATION.md` §7.3). The reconstructed stub:

- declares `MAX_COMPONENTS=4`, `MAX_CYCLES=20`,
  `MAX_ESCALATION_DEPTH=2`, `MAX_MESSAGES_IN_FLIGHT=3`;
- prints these bounds;
- refuses to run TLC (it is a stub, not a runner).

Its new SHA-256 is recorded in `results/.addendum_001.sha256`.

**This new SHA is NOT the original frozen SHA.** The original is lost.
The new SHA is recorded in `results/.addendum_001.sha256`, not in
`results/.preregistration.sha256`.

### 3.3 TLC runner separated

The TLC runner is a **separate, new file**:

    formal/model_check_full.sh

This file is not in the original freeze digest. Its SHA is recorded in
`results/.addendum_001.sha256`.

### 3.4 TLA+ corrections

The TLA+ files in `formal/` are rewritten to fix the technical issues
raised in review. These are corrections of translation, not changes of
hypotheses:

1. **R1–R5 are temporal properties.** Declared as `PROPERTIES` in
   `GatewayPhase2.cfg`, not `INVARIANTS`.
2. **R3 and R4 lacked execution transitions.** `FailLocalRecovery` and
   `ConstraintConflict` are added as explicit transitions so the
   properties are not vacuously true.
3. **`local_action` was never enabled.** `TakeLocalAction` is added,
   guarded by `~constraint_conflict`, so H4 is not vacuously true.
4. **`BoundedEscalation` was mis-stated.** Replaced by
   `EscalationCompletes`, which says: if escalation occurs, a VSM
   resolution follows.
5. **`MAX_ESCALATION_DEPTH` and `MAX_MESSAGES_IN_FLIGHT` were declared
   but not represented.** Both are now `CONSTANTS` in `GatewayPhase2.tla`
   with explicit `ASSUME` clauses, and escalation depth is enforced in
   `Next`.

The new TLA+ files are recorded in `results/.addendum_001.sha256`.

## 4. H5 status: PENDING

H5 is recorded as **PENDING** until an actual, reproducible TLC run
produces a verdict. The following distinctions are enforced:

- Writing TLA+ is **not** a successful formal verification.
- A successful TLC run is **not** an operational safety certification.
- Absence of TLC is **not** a failure of H5; it means verification has
  not yet been executed.

A TLC run, if performed, is logged to
`results/tlc_run_YYYY-MM-DDTHH-MM-SSZ.log` with the exact TLC version,
the exact `.cfg` used, and the exact TLA+ SHAs. A PENDING verdict is not
a pass.
